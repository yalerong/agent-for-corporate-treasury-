这一轮没有配 API Key——那 LLM 到底管什么？

现在这一轮（离线）
  • 角色的那句话 = 确定性模板
  • 金额、缺口、档位、红线 = 代码
  • 你看到的每个数字都不是模型生成的
生产环境（配上 Key）
  • 角色的那句话 = 模型改写摘要
  • 模型还负责从流水里归纳新规律，进候选池等人批
  • 金额、缺口、档位、红线 = 仍然是代码

这是刻意的分工：LLM 总结规律，代码执行规律。模型不可用、网络断了、Key 过期， 判定链路照常出结果——差别只是话说得干不干瘪。

规则是怎么长出来的

每周一轮真实业务复盘，人逐条挑错，裁决入库带出处。模型负责发现候选模式，规则是否进入资金计算只由人决定。

首轮实战形成初始规则沉淀

周度复盘每周实战对流水挑错，错处修订成新规则

口径过严 → 系统性高估

把项目自身成本误报成外部资金缺口

引擎当时怎么做
把 PJA 项目下四个主体的平台费与税费全部报为资金缺口。
实际情况
费用本身属于项目成本，各主体项目户余额足够自足；误报占当周全部资金需求的 31%。
人的裁决
计划行所属项目与账户项目标签一致时，该项目户即为合法弹药。R-031 同族
业务常识缺失

集团内往来不必为币种去购汇

引擎当时怎么做
某主体需支付数百万 CNY 咨询服务费，而 CNY 余额近乎为零，于是建议从美元账户购汇。
实际情况
收款方是集团内另一主体，可按约定汇率入账挂往来。
人的裁决
收款方属集团内时不购汇，直接使用可用币种。R-028
危险误判 · 资金安全

“未见流水”不等于“未付款”

引擎当时怎么做
计划行匹配不到对应付款，便判为未付并进入待付清单。
实际情况
可能是合并支付，也可能是审批已提交但尚未到付款节点；误判会导致重复出款。
人的裁决
付款前按审批编号查流程节点，前两种不得判欠款。R-030
归纳过度 · AI 自我批评

把同期发生误认为固定因果

引擎当时怎么做
从单周记录归纳出“固定走渠道 A 换汇，不占用 USDT 池”。
实际情况
渠道 A 换汇付本币与 USDT 池支付只是两条同期发生、互相独立的腿。
人的裁决
按币种拆成独立资金腿，弹药来源可替换而非固定路径。样本量为 1 时，候选不得直接进计算。R-032
结构性知识缺失 · 账户性质

账上余额不一定是自己的钱

引擎当时怎么做
按账户余额计算可动用资金，把某主体账上的全部余额计入弹药。
实际情况
该账户是受托专用户，资金属于外部受托方，绝不可动用。
人的裁决
受托专用户从可动用口径中整体剔除，主体缺口改由关联方拆借解决。R-022 / R-023
时间错觉 · 排期

「理财到期」不等于「资金可用」

引擎当时怎么做
把定存到期日当作资金可用日，据此判断"账单日的缺口已被到期资金覆盖"。
实际情况
到期当天，数百万美元随即被滚入新一期定存——"到期"与"留在活期"是两回事，而账单日恰好比下一个到期日早一天。
人的裁决
理财到期进"按日可动用"模型，且必须读台账里的"是否续存"标记；到期即滚存的不算可用。R-034

一条规则的生命周期：以“不购汇”为例

模型归纳候选模型能做的只有“看出模式”
标 provisional不进任何计算，错了也不会算进钱里
人工裁决人是唯一能把候选变成规则的角色
approved 入库每条规则钉出处，可按版本重放审计
下一轮生效规则由代码执行，不由模型执行
